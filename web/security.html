Sécurité par conception

Nous ne demandons jamais
vos identifiants bancaires

StatementFlow convertit des fichiers que vous déposez (PDF, CSV, TSV, XLSX). Aucune connexion à votre banque, aucun agrégation de comptes, aucune synchronisation automatique. Vous fournissez un document ; nous renvoyons du JSON ; le document et le résultat disparaissent.

Comment vos relevés sont traités

1 · Dépôt

Vous téléversez un fichier (20 Mo max). Il est lu en mémoire par blocs d'un mégaoctet, avec interruption immédiate si la limite est dépassée — il n'est jamais écrit sur le disque du serveur, jamais archivé, jamais copié.

2 · Conversion

L'extraction se fait entièrement en mémoire. Le résultat reste récupérable 15 minutes via votre clé ou votre session (TTL de 900 secondes), puis il est purgé. Aucun mécanisme de conservation n'existe dans le code.

3 · Après expiration

Seules des métadonnées subsistent dans l'historique : nom du fichier, format, nombre de transactions, crédits consommés, date. Jamais les transactions bancaires elles-mêmes, jamais les soldes, jamais les montants.

Ces garanties ne sont pas des promesses marketing : le code de traitement est public dans le dépôt GitHub (src/statementflow/api.py, fonction _read_upload_capped ; pg.py, table jobs — métadonnées uniquement), et les échantillons de la démo sont les mêmes pour tout le monde.

Mesures techniques vérifiables

🔐 Secrets

Les clés API ne sont stockées que sous forme de hachage SHA-256 ; les mots de passe sous forme de dérivation PBKDF2-SHA256 avec 600 000 itérations et un sel unique par compte. La clé en clair n'est affichée qu'une fois à la création ; une clé perdue se régénère, elle ne se récupère pas.

🚫 Journalisation

Les journaux applicatifs ne contiennent ni clé API, ni mot de passe, ni contenu de relevé. Les comparaisons de secrets se font en temps constant (protection timing). Les noms de fichiers sont nettoyés (anti path-traversal) avant d'être journalisés.

💰 Paiements

Les crédits sont achetés via SasPay. Un paiement n'est validé que sur webhook signé HMAC (rejet au-delà de 5 minutes d'écart) et vérification du statut réel auprès de la passerelle — jamais sur le simple retour du navigateur. Un échec restitue les crédits réservés.

🧱 Limites et quotas

Quotas de documents/pages par clé, limites de taille de fichier (20 Mo), de pages (200) et de lignes (200 000), limitation de débit sur les endpoints sensibles (inscription, connexion, réinitialisation : fenêtre glissante 10 requêtes / 15 minutes). Réservations de crédits atomiques et idempotentes.

🍪 Sessions

Cookies de session HttpOnly, SameSite=Lax, Secure en HTTPS, expiration à 30 jours ; jetons de réinitialisation de mot de passe à usage unique valables 1 heure, jetons de vérification email 48 heures, stockés hachés.

🔎 Transparence

Aucun cookie publicitaire, aucun tracker tiers (Google Analytics, Meta Pixel, etc.) sur aucune page : les événements mesurés (visites, inscriptions, conversions) restent dans notre base. Le code de l'application est public et chaque affirmation de cette page peut y être vérifiée.

Hébergement et sous-traitants

Ce que nous faisons héberger, par qui, et où — sans surenchère.

Render (États-Unis — Oregon, GCP us-west1)

Héberge l'application web et l'API. Les relevés y transitent en mémoire le temps du traitement (quelques secondes), puis sont purgés au TTL. Le service est servi via HTTPS (TLS géré par Render, devant le CDN Cloudflare utilisé par Render).

Supabase (UE — Francfort, AWS eu-central-1)

Héberge la base PostgreSQL : comptes (emails, dérivations de mots de passe), clés API hachées, soldes de crédits, historiques de métadonnées de conversion. Les relevés eux-mêmes n'y sont jamais stockés — le traitement est éphémère et la table des résultats vit en mémoire applicative.

SasPay

Passerelle de paiement pour l'achat de crédits. Reçoit le montant et la référence de la transaction ; ne reçoit ni les documents, ni les données de compte autre que l'identifiant nécessaire au crédit.

GitHub (Microsoft)

Héberge le dépôt de code public. Peut être contacté par quiconque — c'est le principe.

Nos applications tournent sur des régions d'infrastructure qu'il est possible de vérifier indépendamment (DNS public). Si un sous-traitant change, cette page est mise à jour.

Signaler une vulnérabilité

Vous avez trouvé une faille ? Merci de la signaler de façon responsable en ouvrant une issue privée (security advisory) sur le dépôt GitHub, ou par le canal de contact indiqué dans les mentions légales. Nous nous engageons à accuser réception sous 72 heures et à corriger les failles validées en priorité. Merci de ne pas tester sur des données réelles de tiers.

À ce jour, aucun audit de sécurité tiers n'a été réalisé — c'est l'un des compromis d'un service jeune. Le code public et la suite de tests (plusieurs centaines de tests, y compris sur la sécurité : hachage, webhooks signés, isolation entre comptes) sont notre meilleure garantie en attendant.

Ce que nous ne ferons pas

  • Demander vos identifiants bancaires ou un accès à votre banque — le service n'a pas de mode « connexion à la banque » et n'en aura pas ;
  • Conserver vos relevés ou leurs transactions au-delà du TTL de 15 minutes — le code n'en a tout simplement pas la capacité ;
  • Vendre, partager ou exploiter commercialement vos données — aucune donnée bancaire n'est stockée, il n'y a rien à vendre ;
  • Ajouter un tracker publicitaire — il n'y en a aucun aujourd'hui et leur ajout serait visible dans le code public.
